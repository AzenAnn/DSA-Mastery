# 1. 问题驱动与 List ADT (抽象接口定义)

> **本节概述**：本篇为《数据结构与算法》开源项目 Chapter 01 的第 1 篇核心讲义。
> 本篇从现实世界的一维序列数据组织切入，确立软件工程中“接口与实现分离”的面向接口编程思想，并给出规范的 **List ADT (Abstract Data Type)** 接口契约与语义定义。

---

## 1.1 现实问题与数据抽象

### 1.1.1 现实世界中的一维序列模型
在日常生活与各种软件应用中，我们几乎时刻都在与“一排按顺序排列的数据”打交道：

* **音乐播放列表 (Playlist)**：歌曲按照添加时间或播放顺序排成一列。播放器支持按顺序播放下一首、返回上一首、插入新歌以及移出旧歌。
* **浏览器历史记录 (History)**：用户访问网页的 URL 形成了一个严格的时间序列。你可以点击“后退”查看上一页，点击“前进”前往下一页。
* **待办事项清单 (TodoList)**：任务按创建时间或优先级排成清单。每完成一项就从清单中划掉，有新任务时追加到末尾。

虽然这些场景涉及的业务完全不同，但在计算机底层，它们都具备**相同的结构特征**：所有数据元素都按**一维次序**排列。

### 1.1.2 前驱后继关系与线性表抽象
在计算机科学中，我们将具有**一对一（1:1）逻辑关系**的数据元素有限序列，抽象定义为**线性表 (Linear List)**。

若将线性表表示为序列：$L = (a_0, a_1, a_2, \dots, a_{n-1})$，其中 $n \ge 0$ 为表长（$n=0$ 时称为空表），则它必须满足以下严格的逻辑约束：

```
       ┌───────────┐    ┌───────────┐    ┌───────────┐          ┌─────────────┐
       │   a_0     │--->│   a_1     │--->│   a_2     │---> ...->│   a_{n-1}   │
       └───────────┘    └───────────┘    └───────────┘          └─────────────┘
          (首节点)        (中间节点)       (中间节点)               (尾节点)
```

1. **唯一首节点 (Head)**：元素 $a_0$ 是序列的起点，它**没有前驱节点**，有且仅有一个直接后继节点 $a_1$。
2. **唯一尾节点 (Tail)**：元素 $a_{n-1}$ 是序列的终点，它**没有后继节点**，有且仅有一个直接前驱节点 $a_{n-2}$。
3. **内部节点 (Internal Nodes)**：对于任意中间元素 $a_i$ ($0 < i < n-1$)：
   * 有且仅有一个直接**前驱节点 (Predecessor)** $a_{i-1}$；
   * 有且仅有一个直接**后继节点 (Successor)** $a_{i+1}$。

### 1.1.3 物理布局与逻辑抽象的区别
初学者常犯的一个错误是将“逻辑结构”与“物理存储”混为一谈。

* **逻辑结构 (Logical Structure)**：指的是数据元素之间的**抽象关系**（例如这里定义的一对一前驱后继关系）。
* **物理存储 (Physical Storage)**：指的是数据在计算机**内存硬件上的实际存放方式**。

> **核心结论**：
> 逻辑上的“连续”**不等于**物理上的“连续”！
> * 我们可以用一块**物理连续**的内存地址来存储线性表（叫**顺序表**）；
> * 也可以用散落在内存各处、通过指针互相连接的**物理离散**单元来存储线性表（叫**链表**）。

## 1.2 抽象数据类型 (List ADT)

### 1.2.1 面向接口编程 (Interface-Driven Design)
在现代软件工程中，最核心的设计原则之一就是**“解耦 (Decoupling)”**——即将系统的“接口声明”与“具体实现”彻底分开。

* **What (做什么 / 接口)**：上层业务代码只关心“线性表支持哪些操作”（例如插入一个元素、获取某个位置的值）。
* **How (怎么做 / 实现)**：底层数据结构负责考虑“如何在内存中存储和执行这些操作”（例如是用动态数组做，还是用双向链表做）。

```
 +-------------------------------------------------------+
 |                 上层业务应用程序 (Client)               |
 +-------------------------------------------------------+
                             │
                             ▼ 仅依赖抽象规范
 +-------------------------------------------------------+
 |               List ADT 标准接口 (Interface)            |
 +-------------------------------------------------------+
           ▲                                   ▲
           │ 实现 (Implementation)              │ 实现 (Implementation)
 +───────────────────+               +───────────────────+
 |   动态顺序表 Vector  |               |   双向链表 LinkedList |
 +───────────────────+               +───────────────────+
```

通过定义 **ADT (Abstract Data Type)**，我们可以做到：即使未来将底层的顺序表替换为链表，上层业务代码**一行都不需要修改**。

### 1.2.2 核心 API 接口定义与语义规范
我们将线性表的标准操作集合规范化为以下抽象模板接口类：

```cpp
template <typename T>
class List {
public:
    virtual ~List() {}

    // ================= 1. 状态查询接口 =================
    
    /**
     * @brief 获取当前线性表中有效元素的数量
     * @return int 元素个数 n (n >= 0)
     */
    virtual int size() const = 0;

    /**
     * @brief 判断线性表是否为空
     * @return true 表中无元素 (size == 0)
     * @return false 表中有元素 (size > 0)
     */
    virtual bool isEmpty() const = 0;


    // ================= 2. 存取与修改接口 =================
    
    /**
     * @brief 获取指定秩(Rank/下标)处的元素
     * @param rank 元素的索引 (0 <= rank < size())
     * @return T 返回对应位置的数据元素
     */
    virtual T get(int rank) const = 0;

    /**
     * @brief 修改指定秩(Rank/下标)处的元素值
     * @param rank 元素的索引 (0 <= rank < size())
     * @param elem 新的新数据元素值
     */
    virtual void set(int rank, const T& elem) = 0;


    // ================= 3. 结构变更接口 =================
    
    /**
     * @brief 在指定秩(Rank/下标)处插入新元素 elem
     * @details 原 rank 及其之后的元素依次向后平移一位；表长 size 加 1
     * @param rank 插入位置 (0 <= rank <= size())
     * @param elem 待插入的新数据元素
     */
    virtual void insert(int rank, const T& elem) = 0;

    /**
     * @brief 删除指定秩(Rank/下标)处的元素
     * @details 被删除元素之后的元素依次向前平移一位；表长 size 减 1
     * @param rank 待删除位置 (0 <= rank < size())
     * @return T 被删除的元素原值
     */
    virtual T remove(int rank) = 0;
};
```

### 1.2.3 契约规范与边界处理声明
任何严格的 API 必须声明其**契约边界 (Pre-conditions & Post-conditions)**：

1. **秩 (Rank) 的合法范围**：
   * 对于 `get(rank)`、`set(rank, elem)` 和 `remove(rank)`：合法的索引范围是 $0 \le \text{rank} < \text{size()}$。
   * 对于 `insert(rank, elem)`：合法的插入索引范围是 $0 \le \text{rank} \le \text{size()}$（当 $\text{rank} = \text{size()}$ 时表示尾部追加）。
2. **异常契约 (Exception Contracts)**：
   * 若传入的 `rank` 超出上述合法范围，ADT 实现必须抛出 `IndexOutOfBoundsException`（越界异常）或断言终止（`assert`），防止非法访问越界内存。
