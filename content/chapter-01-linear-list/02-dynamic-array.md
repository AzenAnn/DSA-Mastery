# 2. 第一种实现——动态顺序表 (Dynamic Array / Vector)

> **本节概述**：本篇为《数据结构与算法》开源项目 Chapter 01 的第 2 篇核心讲义。
> 本篇深入讲解线性表的第一种底层物理实现——**动态顺序表 (Dynamic Array / Vector)**。剖析其物理内存映射公式、硬件级别的 **CPU Cache 局部性**，并运用**聚合分析法**严密推导乘法扩容的 **$O(1)$ 摊还时间复杂度 (Amortized Analysis)**。

---

## 2.1 物理内存连续性与随机存取

### 2.1.1 物理地址计算公式推导
顺序表 (Sequential List / Vector) 是利用**一段物理地址连续的内存单元**依次存储线性表的数据元素。

假设顺序表首元素 $A_0$ 的物理内存地址为 $Loc(A_0)$，每个元素在内存中占用 $L$ 字节：

$$Loc(A_i) = Loc(A_0) + i \times L$$

正是因为物理内存是连续的，CPU 只需要做一次加法与一次乘法即可直接计算出任意下标 $i$ 的内存地址。这种通过下标存取元素的方式被称为**循秩访问 (Call-by-Rank)**，其时间复杂度为绝对的 **$O(1)$ 随机存取**。

```
内存地址:  0x1000     0x1004     0x1008     0x100C
物理单元: [  A_0  ]  [  A_1  ]  [  A_2  ]  [  A_3  ]
下标(Rank):   0          1          2          3
```

### 2.1.2 硬件视角：CPU Cache Locality (缓存局部性)
为什么遍历顺序表的速度远快于指针离散的链表？
根据计算机体系结构的**空间局部性原理 (Spatial Locality)**，当 CPU 访问内存单元 $Loc(A_i)$ 时，硬件会自动将其相邻的一整块内存（通常为 64-Byte 的 Cache Line）加载到极速的 CPU L1/L2 Cache 中。

遍历顺序表时，后续元素的访问几乎 **100% 命中 Cache**，避免了漫长的主存 (DRAM) 访问延迟。

## 2.2 动态扩容机制与摊还分析 (Amortized Analysis)

### 2.2.1 静态数组容量固定的局限性
传统静态数组（如 `int arr[100]`）在声明时必须指定固定容量 `capacity`。当元素数量超出 `capacity` 时会引发溢出，而预设过大又会导致内存浪费。

为了解决这一矛盾，现代顺序表采用了**动态扩容 (Dynamic Resizing)** 机制。

### 2.2.2 扩容策略对比：加法扩容 vs 乘法扩容
当顺序表满（`size == capacity`）时，必须向操作系统申请一块更大的连续内存，并将旧数据逐一拷贝过去。

1. **加法扩容 (每次容量 $+K$)**：
   假设每次扩容增加 $K$ 个单元。插入 $N$ 个元素需要触发 $N/K$ 次扩容，累计元素拷贝次数为：
   $$\text{Total Copies} = K + 2K + 3K + \dots + N \approx O(N^2)$$
   分摊到单次插入，平均时间复杂度退化为 **$O(N)$**，在工程上是不可接受的。

2. **乘法扩容 (每次容量 $\times 2$ Doubling)**：
   每次扩容将容量翻倍。插入 $N$ 个元素仅触发 $\log_2 N$ 次扩容。

### 2.2.3 聚合分析法 (Aggregate Analysis) 证明
当连续插入 $N$ 个元素（初始容量为 1）：
* 绝大多数普通插入只需 **$1$** 次赋值操作，共 $N$ 次；
* 仅在第 $1, 2, 4, 8, \dots, 2^k$ 次插入时触发扩容，元素拷贝总次数为：
  $$1 + 2 + 4 + 8 + \dots + 2^k < 2N$$

整个序列 $N$ 次插入的总耗时不超过 $N + 2N = 3N$。因此，单次插入的**摊还时间复杂度 (Amortized Time Complexity)** 为：

$$\text{Amortized Cost} = \frac{3N}{N} = O(1)$$

```
插入序号: 1  2  3  4  5  6  7  8  9 ...
扩容拷贝: 1  2     4           8       ...
拷贝代价: ★  ★★    ★★★★        ★★★★★★★★
```

### 2.2.4 动态缩容与防抖动 (Thrashing) 机制
为了防止空间浪费，当元素删除导致利用率过低时需要缩容：
* **错误策略**：当 `size == capacity / 2` 时减半容量。
  * *灾难场景*：在 `capacity` 临界点交替执行 `insert` 和 `remove`，会导致每次操作都触发 $O(N)$ 的重新分配与拷贝。
* **防抖动正确策略**：当装载因子 $\alpha = \text{size} / \text{capacity} < 25\%$ 时才将容量减半。留出 75% 的内存缓冲区，有效平抑了边界震荡。

## 2.3 顺序表上的算法思想延伸 (配合习题铺路)

顺序表不仅是存储结构，其物理连续性还催生了许多高效的算法思想：

### 1. 点查询思想：遍历 $O(n)$ vs 有序二分查找 $O(\log n)$
* **痛点**：在无序顺序表中查找一个元素 $x$，只能从头到尾遍历，最坏需要 $O(n)$ 时间。
* **思想升级**：如果顺序表是**有序**的，利用物理下标支持 $O(1)$ 随机存取的特性，我们可以采用**二分查找 (Binary Search)**：每次对比中点，将搜索区间折半。查找复杂度直接降至 **$O(\log n)$**。
* **📌 对应例题**：LeetCode 704. 二分查找 / LeetCode 35. 搜索插入位置

### 2. 区间查询思想：频繁求和痛点 $\rightarrow$ 前缀和 (Prefix Sum) 预处理 $O(1)$
* **问题引入**：假设给定一个包含 $n$ 个元素的顺序表，我们需要频繁查询任意区间 $[L, R]$ 内所有元素的和。
* **预处理算法思想 (前缀和)**：
  我们额外维护一个前缀和数组 $P$，其中 $P[i]$ 表示前 $i$ 个元素的累加和：$P[i] = P[i-1] + A[i]$。
  经过 $O(n)$ 时间的预处理后，任何区间 $[L, R]$ 的元素和可以直接通过一次减法算出：$\text{Sum}(L, R) = P[R] - P[L-1]$。单次查询时间复杂度直接降至 **$O(1)$**！
* **📌 对应例题**：LeetCode 303. 区域和检索 - 数组不可变 / LeetCode 560. 和为 K 的子数组

## 2.4 顺序表性能总结

| 操作 | 复杂度 | 解释 |
| :--- | :--- | :--- |
| `get(rank)` / `set(rank)` | **$O(1)$** | 内存地址直接计算 (循秩访问) |
| `insert(rank, elem)` (尾部) | **$O(1)$ 摊还** | 乘法 2 倍扩容保障 |
| `insert(rank, elem)` (头部/中间) | **$O(N)$** | 需要将该位置后的所有元素批量后移 |
| `remove(rank)` (头部/中间) | **$O(N)$** | 需要将该位置后的所有元素批量前移 |
