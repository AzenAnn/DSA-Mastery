# 1.5 存储结构的比较与选择

## 学习目标

- 能从时间、空间、缓存局部性三个维度比较顺序表与链表；
- 能根据访问模式为具体场景做出有依据的结构选择；
- 能准确表述「链表插入 O(1)」与「顺序表更快」各自的适用前提；
- 能用「双链表 + 哈希」的框架分析 LRU 缓存，并给出复杂度结论。

## 引入

1.2 与 1.3 分别实现了顺序表和链表。现在的问题是：**同一份线性表，到底该用哪种？** 答案不是「快的就是好的」——两种结构各自有一批 O(1) 操作，也各自有一批 O(n) 操作；更没有「链表一定比顺序表快」或反之的绝对结论。选择由**访问模式**主导：应用中最频繁、对延迟最敏感的操作是什么，就以它为主要判据。本节把比较显式化为三个维度——时间、空间、缓存局部性，再给出决策流程，最后用两个例题检验这套方法。

本节的路线是：先用复杂度表建立量级认识，再用两个定量例子（内存估算、缓存缺失估算）建立常数认识，最后把两者合并成决策流程。判断一个结构是否合适，至少要能回答三个问题：量级可接受吗？常数因子可接受吗？空间代价可接受吗？

## 三维权衡

**时间：操作 × 结构的复杂度**

以下结论均以「动态顺序表」「带头结点的单链表 / 双链表」「带头结点且只保留尾指针的循环单链表」为对象：

| 操作 | 顺序表 | 单链表 | 双链表 | 循环单链表（尾指针） |
| --- | --- | --- | --- | --- |
| 按位置访问 / 修改 | O(1) | O(n) | O(n) | O(n) |
| 按值查找 | O(n) | O(n) | O(n) | O(n) |
| 表头插入 / 删除 | O(n) | O(1) | O(1) | O(1) |
| 表尾插入 | 摊还 O(1) | 有尾指针 O(1) | O(1) | O(1) |
| 表尾删除 | O(1) | O(n) | O(1) | O(n) |
| 已知前驱后的插入 / 删除 | 不适用，仍需搬移 | O(1) | O(1) | O(1) |
| 按位置插入 / 删除 | O(n) | O(n) | O(n) | O(n) |

读表时注意三点：

- 链式结构的 O(1) 都建立在「已持有目标结点或其前驱」的前提上；只给位置时，定位先花 O(n)，完整操作仍是 O(n)；
- 顺序表「表尾插入」标注摊还：平时 O(1)，扩容当次 O(n)（推导见 1.2 节）；
- 循环单链表（尾指针）的表尾删除仍是 O(n)：删除需要前驱，而尾结点的前驱需要遍历定位（见 1.4 节）。

没有任何一种结构在整张表上占优——这正是「由访问模式决定」的原因。

一个定量例子可以说明「同阶不同量」的差距：设表长为 n = 10 万，在表头插入 10 万次。顺序表每次表头插入要搬移「当前全部元素」，总搬移量约 $\frac{n^2}{2} = 5\times 10^9$ 次赋值（第 k 次插入搬移 k-1 个元素），约需数秒；单链表每次表头插入是常数次指针赋值，总操作约 $10^5$ 次，毫秒级完成。两者量级分别是 O(n²) 与 O(n)，但真正的差距来自「每次操作的工作量」——这正是由访问模式决定的：表头频繁插入时，顺序表在量级上就输了，根本轮不到比常数。

**空间：容量利用率与指针开销**

顺序表的空间代价是**未使用的容量**：需要维持 capacity ≥ size，装填因子 size/capacity 通常小于 1；倍增扩容时，扩容当次需同时容纳旧、新两份存储，峰值内存约为 2 倍，搬移完成后旧存储才释放。

链表的空间代价是**每结点一个（或两个）指针域**。以 64 位环境存 int 为例：单链表结点 = 4 字节数据 + 8 字节指针，对齐后至少 12–16 字节；双链表再加 8 字节，约 20–24 字节；若用 malloc 逐结点分配，分配器还要附加每块 16 字节左右的头部，实际开销更大。

估算例子——100 万个 int：

- 顺序表：约 4 MB（100 万 × 4 字节，紧密排列；计入未用容量与扩容峰值，通常仍在 4–8 MB 内）；
- 单链表：每结点至少 12–16 字节，即 12–16 MB；计入分配器头部与对齐后，实际可能达 32–48 MB；
- 双链表：每结点约 20–24 字节，即 20–24 MB，实际可能 40 MB 以上。

结论：链表的空间常数通常是紧凑顺序存储的 3–8 倍。当元素本身很大（每元素数百字节）时指针开销占比下降，差距缩小；当元素很小（int、char）时，指针开销可能反超数据本身。

顺序表的两项空间推导：

- **平均装填因子**：倍增扩容策略下，容量从 $2^{k}$ 翻到 $2^{k+1}$，之后用到 $2^k$ 才再次扩容，故装填因子始终落在区间 $[1/2, 1)$，平均约 3/4。若采用「每次只加固定容量」的扩容策略，平均装填因子可以更高，但扩容次数与搬移总量也会上升——装填因子与扩容代价是此消彼长的；
- **扩容峰值内存**：扩容瞬间旧数组与新数组同时存在，峰值约为新容量的存储量（旧的一份 + 新的一份），搬移完成后旧存储才释放。对 100 万个 int 的顺序表，若容量倍增到 2 倍，峰值约为 8 MB，之后回落到 4 MB 左右。

这两条推导说明：顺序表的空间代价不是「恰好 n 个元素」，而是「容量区间内的任意值」加「扩容当次的 2 倍峰值」。

**缓存局部性**

现代 CPU 以缓存行（cache line，通常 64 字节）为单位从内存取数，并配备硬件预取器。顺序表遍历时地址连续递增，一次取入的缓存行可服务连续多个元素，预取器还能提前取下一行——顺序扫描几乎以内存带宽进行。链表则相反：malloc 随机分配使结点散布在堆的各处，每访问一个 next 都可能落空一次缓存，且一个 64 字节缓存行里往往只有一两个结点，利用率很低。

Sedgewick 与邓俊辉都讨论过这一现象：在缓存层次下，链表的常数因子明显劣于数组，数组的顺序遍历通常比链表快一个数量级左右（Sedgewick《Algorithms》§1.3；邓俊辉《数据结构（C++ 语言版）》第 2–3 章）。由此得到一个常被忽视的结论：**按值查找两边都是 O(n)，但顺序表的顺序扫描常数通常小得多**——n 很大时，理论上的「同阶」在实测中可能差出 5–10 倍。

缺失次数的估算可以量化这一点：顺序表顺序扫描 100 万个 int，数据共约 4 MB，按 64 字节缓存行计算，理想情况下约 6.25 万次缓存行缺失；链表遍历同样 100 万个结点，每个结点几乎都落在不同的缓存行，缺失次数接近 100 万次——相差约 16 倍，且这还不计预取器对顺序访问的加成。这就是「两个 O(n) 不等价」的物理来源。

## 决策依据

**主判据：访问模式。** 先列出频率最高的三五个操作，再看它们在候选结构上的复杂度与常数：

- 随机访问为主（按下标读写，增删少）→ 顺序表；
- 频繁在已知位置附近增删、或在表头/表尾增删 → 链表（两端都要动时优先双链表或带尾指针的循环链表）；
- 遍历与按值查找为主 → 顺序表（常数因子）。

**次判据：其余约束。**

- 规模可预期性：规模变化剧烈且无法预测时，顺序表有扩容摊还代价与峰值内存；链表逐个分配更平滑但更碎；
- 内存限制：元素小而数量巨大时，指针开销可能超过数据本身；
- 迭代器 / 引用失效：顺序表的插入删除会使后续下标与既有引用失效；链表的插入删除只影响相邻结点；
- 实现复杂度：顺序表代码简单、边界少；双链表与循环链表的边界条件多，出错面大；
- 迭代器失效的典型场景：浏览器标签列表在中间插入一个标签后，后续标签的下标全部加 1，任何「记住旧下标」的引用都失效；而链表插入只影响相邻两个结点的指针，已持有的结点引用保持有效。若应用长期持有元素引用并频繁增删，链表在语义上更稳；
- 接口语义：若需要在「遍历过程中删除当前元素」，链表只需先保存下一个结点再删除，顺序表则要小心下标前移带来的越界——这类语义约束有时比性能更能决定结构。

**决策流程表**：

| 场景特征 | 判据 | 推荐 |
| --- | --- | --- |
| 按下标随机访问为主，增删极少 | 访问 O(1) vs O(n) | 顺序表 |
| 表头 / 表尾操作频繁，中间很少动 | 两端 O(1) | 单链表（头）、带尾指针的循环单链表或双链表（尾） |
| 已知位置附近反复插入删除 | 局部修改 O(1) vs O(n) 搬移 | 链表；双向移动多则双链表 |
| 遍历 / 按值查找为主 | 同为 O(n)，比常数因子 | 顺序表 |
| 元素极小、数量百万级 | 指针开销 3–8 倍 | 顺序表（除非增删集中在两端） |
| 规模完全不可预期 | 扩容峰值 vs 逐结点分配 | 两者皆可，顺序表倍增通常更省事 |

一个走查示例：通讯录应用，存储约 1 万条记录，实际使用中约九成操作是按姓名顺序浏览（顺序遍历），其余是新增与删除，且删除多发生在浏览到的当前位置附近。按主判据：遍历与按值查找为主 → 顺序表；次判据：规模可预期（1 万条）、指针开销对每条几百字节的记录占比不大 → 顺序表依然合适，虽然「删除当前位置」在链表上是 O(1)。若使用模式变成「在浏览过程中连续大量删除相邻条目」，则主判据转向「已知位置附近增删」，推荐改为双链表——这就是访问模式变了、结论随之反转的例子。

这套流程的失败模式也很典型：只比较最显眼的一个操作（例如「我们经常插入」）就下结论，忽略其余操作的频率；或者把「量级」与「速度」混为一谈。完整的做法是把三个最高频的操作都写出来，逐格对照复杂度表，再做空间与缓存两项检查——缺一步都可能选错。

## 表述的严谨性

两句话经常被误用，需要把前提说全：

- **「链表插入 O(1)」**的准确说法是：在**已持有目标结点或其前驱**的前提下，链接修改本身是 O(1)；若只给出位置，定位还需 O(n)。只说「插入 O(1)」而不交代前提，是把「局部修改」的复杂度冒充成「完整操作」的复杂度；
- **「顺序表比链表快」**只对**按下标访问与顺序遍历**成立；对「表头插入」「已知位置连续增删」，结论反转。严谨的说法是「对某类访问模式，某结构更合适」，而不是「某结构更快」；
- **「尾部追加 O(1)」**也要区分实现：顺序表是摊还 O(1)（扩容当次 O(n)），单链表必须维护尾指针，双链表与带尾指针的循环链表才是稳定 O(1)——同一句话在不同结构上的含义并不相同。

## 例题讲解

### 例 1：三个场景的结构选型（难度：★★★）

**题目**：为下列三个场景各选择一种线性表实现，说明理由，并各给出一个使结论反转的条件。

(a) 文本编辑器的行缓冲区：行数动态变化，支持在任意行号前后插入、删除行，显示时从头到尾顺序渲染；
(b) 操作系统进程就绪队列：新进程从尾部进入，调度器从头部取出；
(c) 稀疏一元多项式 $P(x) = 3x^{1000} + 2x^2 - 1$ 的存储：项数远小于指数范围，需要按指数归并、计算。

**思路分析**：对每个场景列出高频操作，对照复杂度表与常数因子，先筛掉量级不可接受的结构，再用空间与局部性比较剩余选项。

**答案**：

(a) 推荐顺序表（数组，元素为指向行内容的指针）。理由：渲染是顺序遍历，顺序表局部性最好；按行号定位 O(1)；插入、删除行时搬移的是指针数组，每元素只是一条指针，搬移成本低。**反例条件**：若行数很大且插入删除异常频繁（每次操作都搬移大量指针），或编辑器需要「从任意行起前后移动光标」的双向遍历，双链表更合适。

(b) 推荐循环数组队列（顺序表实现）；若容量完全不可预期，可用带尾指针的循环单链表。理由：尾部入、头部出，循环数组两端均 O(1) 且空间紧凑；链表逐个分配，免去扩容搬移。**反例条件**：若支持「按优先级取出」或「在队列中间删除任意进程」（如进程被终止），两端结构都不行，需要按优先级组织的结构；若只做中间删除，可考虑双链表加哈希定位（见例 2 的思路）。

(c) 推荐单链表，每结点存（系数，指数），按指数降序排列。理由：指数范围可能达 $10^5$ 以上而项数仅几十，若用「指数作下标」的数组，空间浪费是天文数字；链表只存实际存在的项。加法、乘法用双指针归并即可。**反例条件**：若指数范围小而项数接近范围大小（稠密多项式），直接用数组存系数更紧凑，且求值、乘法更快。

**复杂度分析**：(a) 定位 O(1)，插入/删除 O(n)（n 为行数，移动指针），渲染 O(n)；(b) 入队、出队摊还 O(1)；(c) 归并相加 O(p + q)（p、q 为项数），按指数定位 O(项数)。最坏与平均一致——这里的量级由访问路径长度决定，与数据分布无关。

**常见错误与变式**：不看访问模式而只看单个操作的复杂度；把「插入频繁」一律等同于链表——若插入总发生在表尾，顺序表摊还 O(1) 并不差。变式：把 (b) 改成「按 key 快速删除任意元素」的双端结构，就是例 2 的问题框架。

### 例 2：简版 LRU 缓存（难度：★★★）

**题目**：实现容量固定的 LRU（最近最少使用）缓存：`get(key)` 命中时返回值并把该键标记为最近使用；`put(key, value)` 不存在时插入，超过容量则淘汰最久未使用的键。分别分析顺序表版、单链表版、双链表 + 哈希版的时间复杂度，并给出双链表版的核心代码骨架。

**思路分析**：LRU 需要两个能力：(1) 快速定位任意 key 对应的结点（查找）；(2) 把被访问结点移到「最近使用」位置、把「最久未用」结点摘走（局部修改）。查找与局部修改的组合决定结构选择：

- **顺序表版**：按 key 线性查找 O(n)；约定「表头为最近使用、表尾为最久未用」，命中后把元素移到表头需搬移 O(n) 个元素，淘汰表尾元素为 O(1)。整体 O(n)；
- **单链表版**：查找 O(n)；找到结点后移表头需要它的前驱，又需 O(n)；淘汰尾结点要找倒数第二个，O(n)。整体 O(n)，且常数不比顺序表好；
- **双链表 + 哈希表**：哈希表（第 6 章内容，这里只讲思路）把 key 映射到结点指针，查找 O(1)；双链表按「表头 = 最近使用、表尾 = 最久未用」维护顺序；命中时摘出结点移到表头 O(1)，淘汰时删尾 O(1)。整体 O(1)。

「双链表 + 哈希」的组合值得记下：哈希解决「按 key 定位」，双链表解决「维护访问顺序」，两种结构各管一件事，互不干扰。这是「组合优于单点优化」的典型——任何单一结构都同时承担定位与排序两种职责，必然有一项是 O(n)。

**算法步骤**（伪代码）：

```text
数据结构: 哈希表 key -> 结点指针; 循环双链表(带头尾哨兵), 表头为最近使用
get(key):
    p = hash[key]
    if p 不存在: return 未命中
    move_to_front(p)              // 摘出并移到表头, 标记最近使用
    return p->value
put(key, value):
    if key 已存在: 更新 value; move_to_front(p); return
    新建结点 s(key, value), 插入表头
    if 结点数 > 容量:
        摘除尾哨兵前一个结点并 free, 从哈希表删除对应 key
```

**C 实现**（骨架：结点定义、移到表头、淘汰尾结点；哈希表部分以注释说明）：

```c
/* LRU 缓存的双链表骨架 (哈希表实现见第 6 章, 此处以注释代替) */
#include <stdlib.h>

typedef struct LRUNode {
    int key;
    int value;
    struct LRUNode *prev;      /* 前驱 */
    struct LRUNode *next;      /* 后继 */
} LRUNode;

typedef struct {
    int capacity;              /* 容量 K */
    int size;                  /* 当前结点数 */
    LRUNode *head;             /* 哨兵头: head->next 为最近使用 */
    LRUNode *tail;             /* 哨兵尾: tail->prev 为最久未用 */
} LRUCache;

/* 把结点 p 摘出并移到表头 (标记为最近使用) */
void move_to_front(LRUCache *c, LRUNode *p) {
    p->prev->next = p->next;   /* 从原位置摘出 */
    p->next->prev = p->prev;
    p->prev = c->head;         /* 接到哨兵头之后 */
    p->next = c->head->next;
    c->head->next->prev = p;
    c->head->next = p;
}

/* 淘汰最久未用 (尾哨兵前一个结点), 返回其 key 供哈希表删除 */
int evict_tail(LRUCache *c) {
    LRUNode *p = c->tail->prev;    /* 缓存非空时 p 必存在 */
    int key = p->key;
    p->prev->next = p->next;       /* 摘出 */
    p->next->prev = p->prev;
    free(p);                       /* 释放结点 */
    c->size--;
    return key;
}
```

**复杂度分析**：每个操作至多常数次指针调整加一次哈希访问，get 与 put 均为 O(1)（含哈希表扩容时为摊还 O(1)）；空间 O(K)，K 为容量。对照三种方案：顺序表与单链表都是 O(n) 的完整操作，双链表 + 哈希通过「哈希解决查找、双链表解决局部修改」把两者都降为 O(1)——这是「两种结构各取所长」的典型用法。

**常见错误与变式**：

- 边界：容量为 1 时，摘出 p 与移到表头的两步要正确处理唯一结点；
- 淘汰结点后忘记同步删除哈希表中的对应项，留下悬空指针；
- 变式：若淘汰策略改为「先入先出」（FIFO），不需要 move_to_front，结构退化为普通队列；若访问模式完全随机（无局部性），LRU 的命中率收益会下降；若容量极小（如 K = 1），LRU 退化为「永远保留最后访问的一项」，双链表退化为单结点，直接用一个变量即可实现。

## 易错点

1. **只看复杂度表，不看前提**：「插入 O(1)」的前提是已知前驱；「表尾 O(1)」要区分插入与删除；
2. **忽视缓存与常数因子**：两个 O(n) 并不相等，顺序遍历时顺序表的常数通常小一个数量级；
3. **绝对化表述**：「链表永远更快」「顺序表适合一切场景」都是错的，严谨的结论必须带上访问模式与前提；
4. **混淆「摊还 O(1)」与「每次 O(1)」**：顺序表表尾插入在扩容当次是 O(n)，摊还意义下才平均 O(1)；
5. **用「局部修改复杂度」替代「完整操作复杂度」**：完整操作 = 定位 + 修改，定位的 O(n) 不能省略。

## 小结

顺序表与链表不是对手，而是互补工具。时间维度给出量级，空间维度给出常数与峰值，缓存维度给出实测系数。决策流程是：先列出高频访问模式，用复杂度表筛掉量级不可接受的结构，再用空间与局部性比较剩余选项，最后把结论表述为「对该访问模式更合适」而不是「更快」。真正的功力在于把每个复杂度结论的前提说清楚——前提不明，比较就失去了意义。遇到「表头频繁插入」「已知位置连续增删」「百万级小元素」这类特征场景时，应当能立即想起本节的结论，而不是重新争论两种结构谁更优越。
