# 1.1 线性表的定义与抽象数据类型

## 学习目标

- 能用「有限、有序、同类型」三个特征刻画线性表的逻辑结构，说清表头、表尾与直接前驱/直接后继；
- 能用 (D, R, P) 三元组与操作契约表描述线性表 ADT，逐操作写清前置条件、后置条件与失败方式；
- 能论证 get 与 insert 的合法下标域，并在 0 起始与 1 起始（严蔚敏）两种写法之间换算；
- 能理解复杂度预算的作用，并能设计不依赖具体存储结构的黑盒测试。

## 引入：从通讯录与排队叫号说起

先看两个日常例子。

**通讯录。** 手机通讯录存放若干联系人，每个联系人有姓名、电话等属性。用户经常做的操作是：在末尾追加一个新联系人、删除某人、按姓名查找、修改某个联系人的电话。无论通讯录在手机里最终以什么方式存储，这些操作本身是确定的：追加、删除、查找、修改。

**排队叫号。** 银行网点用叫号系统维护等待顾客的次序：新顾客到来时排在队尾，柜台叫号时队首的顾客离开。顾客之间的唯一关系是「谁在谁前面」——排在第 3 位的人知道前一位和后一位是谁，但不需要知道第 10 位是谁。

两个例子内容完全不同，结构却一致：**若干个元素排成一条线，元素之间有明确的前后次序**。把这种结构抽象出来，就得到线性表。从例子中可以提炼出线性表的三个特征：

- **有限**：元素个数是一个确定的非负整数，通讯录不会无限长；
- **有序**：元素按位置排列，次序本身携带信息，交换两个元素的位置会改变表的内容；
- **同类型**：所有元素属于同一个类型，可以统一处理。

注意这里的「有序」指**线性次序**（哪个元素排在第几个位置），与「按值从小到大排序」的含义无关。本章总览见 [00-overview](./00-overview.md)。

## 线性表的逻辑结构

**定义。** 线性表（Linear List）是由 $n\ge 0$ 个同类型元素组成的有序序列：

$$L=(a_0,a_1,\dots,a_{n-1})$$

其中 $n$ 称为线性表的**长度**；$n=0$ 时称为**空表**。$a_0$ 称为**表头**（首元素），$a_{n-1}$ 称为**表尾**（末元素）。$a_i$ 在表中的位置称为**位序**（下标、索引）。

**直接前驱与直接后继。** 对 $1\le i<n$，$a_{i-1}$ 是 $a_i$ 的**直接前驱**，$a_i$ 是 $a_{i-1}$ 的**直接后继**。线性关系的特点可以一句话概括：

- $a_0$ 没有直接前驱，$a_{n-1}$ 没有直接后继；
- 其余每个元素有且仅有一个直接前驱、一个直接后继。

「每个元素至多一个前驱、至多一个后继」正是线性关系的严格定义，也是它与树（一个元素可有多个后继）、图（前驱后继不受限）的本质区别。

**下标约定与教材对照。** 本站统一从 0 起始：$L=(a_0,a_1,\dots,a_{n-1})$，合法位序为 $0\le i<n$。严蔚敏《数据结构（C语言版）》等国内教材从 1 起始，写作 $L=(a_1,\dots,a_n)$（严蔚敏 §2.1）。两种写法位序差 1：本站位序 $i$ 对应严蔚敏写法中的第 $i+1$ 个位置，其合法域为 $1\le i\le n$。阅读任何教材或代码前，先确认其下标约定。

**逻辑结构与存储结构必须分开。** 线性表描述的是**元素之间的逻辑关系**，属于**逻辑结构**；至于元素在计算机里是存放在一段连续空间（**顺序表**），还是用指针串成链（**链表**），属于**存储结构**（严蔚敏 §2.1、王道 2.1）。同一个逻辑结构可以有多种存储结构，同一段内存也可以解释为不同的逻辑结构。把「线性表」与「数组」混为一谈、以为线性表天然带下标，都是没有把这两层分开。本章的 [顺序表](./02-sequential-list.md) 与[单链表](./03-singly-linked-list.md) 两节，讨论的正是同一逻辑结构的两种存储实现。

## 抽象数据类型：用 (D, R, P) 描述

**抽象数据类型**（Abstract Data Type，ADT）是「一个数学模型以及定义在该模型上的一组操作」（严蔚敏 §2.1），形式化地记为三元组：

$$\text{ADT LinearList} = (D,\ R,\ P)$$

其中：

- **数据对象 D**：线性表中元素的取值范围。对通讯录而言，D 是所有联系人记录的集合；对通用线性表，D 是元素类型 ElemType 的值集合。
- **数据关系 R**：元素之间的线性次序。设 $L=(a_0,a_1,\dots,a_{n-1})$，则

$$R=\{\langle a_{i-1},a_i\rangle\mid 1\le i<n\}$$

  即所有相邻元素对 $\langle a_0,a_1\rangle,\langle a_1,a_2\rangle,\dots,\langle a_{n-2},a_{n-1}\rangle$ 构成关系。从这个集合可以直接读出：$a_0$ 只出现在关系的前位而不出现在后位（无前驱），$a_{n-1}$ 只出现在后位（无后继）。
- **基本操作 P**：定义在 D 上的操作集合，即下一节的契约表。

ADT 的价值在于**用户视角**：使用者只看到「能做什么」与「做到什么程度」，看不到「怎么做的」。存储结构可以整体替换，而 ADT 保持不变——这是后续顺序表与链表能够共享同一套测试的根本原因。

## 操作契约表

本站线性表 ADT 采用 0 起始下标，基本操作为：

| 操作 | 前置条件 | 后置条件 | 失败方式 |
| --- | --- | --- | --- |
| `size()` | 无 | 返回当前元素个数 $n$ | 不会失败 |
| `is_empty()` | 无 | 空表返回真，否则返回假 | 不会失败 |
| `get(i)` | $0\le i<n$ | 返回位序 $i$ 的元素，表不变 | 越界时失败 |
| `set(i, v)` | $0\le i<n$ | 位序 $i$ 的元素变为 $v$，长度不变 | 越界时失败 |
| `insert(i, v)` | $0\le i\le n$ 且容量允许 | 表变为 $(a_0,\dots,a_{i-1},v,a_i,\dots,a_{n-1})$，长度 $+1$ | 越界或表满时失败 |
| `remove(i)` | $0\le i<n$ | 删除并返回位序 $i$ 的元素，其后元素位序前移，长度 $-1$ | 越界（含空表）时失败 |
| `find(v)` | 无 | 返回 $v$ 首次出现的位序；不存在时返回约定值 $-1$ | 未找到按约定返回值，不算异常 |
| `clear()` | 无 | 删除全部元素，回到空表 | 不会失败 |

需要强调的细节：

- `insert(i, v)` 的合法域比 `get` 多一个位置 $i=n$，对应在表尾追加，理由见例 2；
- `remove` 的后置条件写明「其后元素位序前移」，这是删除在逻辑结构上的效果，与存储方式无关；
- `find` 的失败方式与 `get` 不同：未找到是查找的**正常结果**（$v$ 本来就可能不在表中），返回 $-1$ 即可；`get` 越界则是**调用方违约**，应当报错。

## 边界约定与失败方式

契约表里每一行都写了失败方式，这不是形式主义。接口设计必须在一开始统一回答几个问题，否则不同实现会各行其是。

**失败方式的三种策略。** 当操作的前置条件被违反时：

1. **特殊值**：返回一个不可能与正常结果混淆的哨兵值，如 `get` 返回 $-1$、`find` 返回 `NULL`。优点是开销小、无需异常机制；缺点是当 $-1$ 本身可能是合法元素时产生歧义，且调用方可能忘记检查。
2. **异常**：抛出如 `IndexOutOfBoundsException` 的异常中断执行。优点是失败信息明确、不可被忽略；缺点是控制流被打断，要求调用方有异常处理纪律，且 C 语言没有内建的异常机制。
3. **Result 对象**：返回「成功与否 + 结果」的复合对象。C 的「布尔返回值 + 出参」、Rust 的 `Result<T, E>`、TypeScript 的可空联合类型都属于这一类。优点是失败与结果同样显式；缺点是调用略繁琐。

三种策略本身没有绝对优劣，**关键是全接口统一**：不能在 `get` 用特殊值、在 `remove` 又改抛异常。语言习惯也影响选择：C 惯用「返回 0/1 表示失败/成功，结果经出参带回」；Java 惯用异常，越界抛 `IndexOutOfBoundsException`；TypeScript 惯用返回 `undefined` 或抛出 `Error`。本页 C 示例统一采用「返回布尔值 + 出参」的 C 惯用法。

**元素能否为空值。** 若元素类型允许空值（`NULL`、`null`、`undefined`），契约必须明确回答：`find(v)` 是否允许查找空值？`remove` 的返回值是否可能为空？若允许，特殊值策略与结果对象策略都需要重新评估——哨兵值可能被合法空值撞车。建议在契约中显式声明「元素不允许为空值」，并为 `find` 约定哨兵位序 $-1$。

## 算法与实现：从契约到接口

契约先于实现。把 ADT 落到代码上，第一步不是写存储结构，而是用函数原型**冻结接口**：任何实现（顺序表、单链表）都必须提供同一组签名与同一套语义。

```text
// 伪代码：线性表 ADT 的接口
ADT LinearList:
    size() -> int          // 返回元素个数
    is_empty() -> bool     // 空表返回真
    get(i) -> elem         // 按位序取元素，越界失败
    set(i, v)              // 按位序改元素，越界失败
    insert(i, v)           // 在位序 i 前插入，i = size() 即表尾追加
    remove(i) -> elem      // 删除并返回位序 i 的元素
    find(v) -> int         // 返回 v 首次出现的位序，未找到返回 -1
    clear()                // 回到空表
```

```c
/* 接口层：只声明行为，不规定存储结构（C99 可编译） */
typedef int ElemType;                 /* 元素类型；可用 typedef 泛化为其他类型 */

typedef struct LinearList LinearList; /* 不透明句柄：实现内部决定存储方式 */

int  ll_size(const LinearList *L);          /* 返回元素个数 */
int  ll_is_empty(const LinearList *L);      /* 空表返回 1，否则返回 0 */
int  ll_get(const LinearList *L, int i, ElemType *out);   /* 越界返回 0 */
int  ll_set(LinearList *L, int i, ElemType v);            /* 越界返回 0 */
int  ll_insert(LinearList *L, int i, ElemType v);         /* 越界或表满返回 0 */
int  ll_remove(LinearList *L, int i, ElemType *out);      /* 越界返回 0 */
int  ll_find(const LinearList *L, ElemType v);            /* 未找到返回 -1 */
void ll_clear(LinearList *L);                             /* 回到空表 */
```

调用方只依赖这份接口：写测试、写业务代码都不需要知道 `LinearList` 内部是数组还是指针链。这正是例 3 中「契约测试可以原样迁移」的前提。

## 复杂度预算：契约中写下的期望

ADT 不规定实现，因此不承诺任何复杂度——但它可以**设定期望复杂度**，作为实现必须满足的预算：

| 操作 | 顺序表期望 | 单链表期望 | 说明 |
| --- | --- | --- | --- |
| `get(i)` | $O(1)$ | $O(n)$ | 连续存储按下标直接定位；链表需从表头遍历 |
| `set(i, v)` | $O(1)$ | $O(n)$ | 同上 |
| `insert(i, v)` | 最坏 $O(n)$ | 已知前驱时 $O(1)$ | 顺序表需移动元素 |
| `remove(i)` | 最坏 $O(n)$ | 已知前驱时 $O(1)$ | 顺序表需移动元素 |
| `find(v)` | $O(n)$ | $O(n)$ | 两种存储都只能按值扫描 |

预算的意义在于防止「结果正确但实现退化」：若顺序表的 `get` 被实现成线性扫描，接口行为完全正确，却违背了 $O(1)$ 的预算，使用者在不知情的情况下会把全表访问写成 $O(n^2)$。把复杂度写进文档，就是让「正确」与「达标」成为两个都受约束的指标；最坏、平均、摊还等分析口径，在本章例题中逐个演示。

## 教材对照：ADT 的三种视角

「接口与实现分离」是主流教材的共同立场，但叙述角度不同：

- **CLRS** 把栈、队列、链表放在第 10 章「基本数据结构」，先定义每种结构的操作语义，再分别用数组与指针给出实现（CLRS 第 10 章开头与 §10.1）。「先讲操作、后讲实现」的次序就是 ADT 视角。
- **Sedgewick** 在《Algorithms》§1.2「数据抽象」中强调：先写 API，再讨论实现；API 是使用者与实现者之间的契约，调用方只看 API（Sedgewick §1.2）。
- **国内教材**（严蔚敏、王道、邓俊辉）强调「逻辑结构 / 存储结构」二分法：先定义逻辑结构（数据 + 关系），再讨论存储结构（顺序 / 链式），ADT 是两者之间的抽象层（严蔚敏 §2.1、王道 2.1、邓俊辉第 2 章开头）。

三种视角殊途同归：**先冻结「能做什么」，再讨论「怎么存」**。本页采用的 (D, R, P) 三元组即严蔚敏体系的记号。

## 例题讲解

### 例 1：通讯录的最小 ADT（难度：★）

**题目。** 为手机通讯录设计一个最小可用的 ADT：联系人是（姓名，电话）记录；用户需要添加、删除、按位序或按姓名查找、修改、统计个数。请归纳数据对象 D、操作集 P 与契约表。不需要写代码。

**思路分析。** 从需求出发而不是从现成接口出发。逐条列出真实操作：添加联系人（追加）、删除（按姓名）、查找（按姓名，也可按位序翻看）、修改电话、数人数。删除与查找各有两个候选键：位序与姓名。位序是线性表的天然坐标，姓名更贴近用户直觉，两者都保留，但**以位序操作为基础操作**——按姓名的操作可以用位序 + 查找组合表达，这样该 ADT 与通用线性表契约保持一致，后续存储实现可以复用。

**算法步骤（伪代码）。** 本题为设计题，伪代码即归纳过程：

```text
步骤 1  列出使用场景：添加、删除、按名查找、翻看第 i 个、改电话、数人数
步骤 2  提取原子操作：size / is_empty / get(i) / set(i, v) / insert(i, v)
        / remove(i) / find_by_name(name)
步骤 3  划定边界：位序合法域 [0, n)；空表上 get/remove 失败；
        按名删除未找到时失败
步骤 4  统一失败方式：越界与未找到一律返回失败标志，不抛异常
```

**C 实现。** 本题为设计题，不要求实现；契约预算见下。

**复杂度分析。** 无算法执行，以期望预算代替：`get(i)` 期望 $O(1)$；`find_by_name`、`remove_by_name` 最坏 $O(n)$（需扫描姓名）；`insert` 表尾追加期望 $O(1)$（顺序表扩容后摊还），表头插入最坏 $O(n)$。设计阶段写下预算，实现阶段才有验收标准。

**常见错误与变式。** 常见错误：只保留按姓名操作而丢掉位序操作，无法表达「翻到第 $i$ 个联系人」这类需求；或直接把「联系人」设计成数组，把存储结构混入 ADT。变式：若需求是「删除所有同名联系人」，应将 `remove_by_name` 的后置条件改为「删除所有匹配项」，并在契约表中注明循环语义。

### 例 2：get 与 insert 的合法下标域（难度：★）

**题目。** 论证 `get(i)` 的合法域为 $0\le i<n$，`insert(i, v)` 的合法域为 $0\le i\le n$，解释为什么 insert 比 get 多一个合法位置；并对照严蔚敏 1 起始写法（$1\le i\le n$ 与 $1\le i\le n+1$）。

**思路分析。** get 读的是「已经存在的元素」：表有 $n$ 个元素，占据位序 $0,1,\dots,n-1$，因此 $i=n$ 没有元素可读。insert 插入的是「一个尚不存在的位置」：新元素插在位序 $i$ 的元素之前，当 $i=n$ 时插在所有元素之后，即表尾追加。逐项核验：空表（$n=0$）时 $0\le i\le n$ 恰为 $\{0\}$，只在表头（也是表尾）插入，合法；$n=1$ 时合法域为 $\{0,1\}$，既可插在唯一元素之前，也可追加在其后。结论：**「读」的域是 $n$ 个元素的位置，「插」的域是 $n+1$ 个空隙**。换算到严蔚敏 1 起始写法，位序整体右移 1，get 为 $1\le i\le n$，insert 为 $1\le i\le n+1$（严蔚敏 §2.1），两种写法之间的差始终是 1。

**算法步骤（伪代码）。**

```text
function seqlist_get(L, i):
    if i < 0 or i >= L.size:      // 合法域 [0, size)，i == size 时无元素可读
        return 失败
    return L.data[i]

function seqlist_insert(L, i, v):
    if i < 0 or i > L.size:       // 合法域 [0, size]，i == size 表示表尾追加
        return 失败
    if L.size == MAX_SIZE:        // 容量约束
        return 失败
    for j = L.size down to i+1:   // 从后向前移动，避免覆盖
        L.data[j] = L.data[j-1]
    L.data[i] = v
    L.size = L.size + 1
```

**C 实现。**

```c
#include <stdbool.h>   /* C99 起可用 bool */

#define MAX_SIZE 100

typedef int ElemType;  /* 元素类型；可用 typedef 泛化为其他类型 */

typedef struct {
    ElemType data[MAX_SIZE];
    int size;          /* 当前元素个数 */
} SeqList;

/* get：按位序取元素；合法域 0 <= i < size，越界失败 */
bool seqlist_get(const SeqList *L, int i, ElemType *out) {
    if (i < 0 || i >= L->size) {   /* 越界检查：i == size 也没有元素可读 */
        return false;
    }
    *out = L->data[i];
    return true;
}

/* insert：在位序 i 前插入；合法域 0 <= i <= size，i == size 即表尾追加 */
bool seqlist_insert(SeqList *L, int i, ElemType v) {
    if (i < 0 || i > L->size || L->size >= MAX_SIZE) {
        return false;              /* 越界或表满时失败 */
    }
    for (int j = L->size; j > i; j--) {
        L->data[j] = L->data[j - 1];   /* 从表尾起依次后移一个位置 */
    }
    L->data[i] = v;
    L->size++;
    return true;
}
```

**复杂度分析。** 边界检查本身 $O(1)$。`seqlist_get` 常数时间 $O(1)$。`seqlist_insert` 的代价在移动：位序 $i$ 处插入需移动 $n-i$ 个元素，最坏（$i=0$，表头插入）$O(n)$；若 $i$ 在 $[0,n]$ 上均匀分布，平均移动 $\frac{n+0}{2}\approx n/2$ 个，仍为 $O(n)$；表尾追加（$i=n$）只需 $O(1)$。

**常见错误与变式。** 常见错误：把 get 的合法域误写成 $0\le i\le n$，越界一个位置读到不存在的元素；insert 的检查误用 $<$ 而非 $\le$，导致无法表尾追加；移动循环方向写反，从前向后移动会覆盖尚未移动的元素。变式：把「按位序插入」改为「在元素 $v$ 之后插入」，合法域从「位置」变成「值」，需先用 find 定位，这是链表中更常用的操作形态。

### 例 3：remove(i) 的契约与黑盒测试（难度：★★）

**题目。** 为 `remove(i)` 写出前置条件与后置条件；设计一组不依赖存储方式的黑盒测试序列（伪代码级），覆盖空表、表头、表中、表尾、越界、重复元素六类情形；说明这组测试为何能原样迁移到顺序表与链表两种实现。

**思路分析。** 前置条件从契约表照抄：$0\le i<n$；空表时 $n=0$，任何 $i$ 都越界，故空表被前置条件天然排除。后置条件要写满三件事：返回被删元素；长度减 1；位序大于 $i$ 的元素全部前移一位，其余元素相对次序不变。黑盒测试只通过 ADT 接口构造输入、检查输出，不触碰内部数组或指针，因此与存储方式无关。

**算法步骤（伪代码）。**

```text
// 测试序列：所有断言只使用 ADT 接口
function test_remove(L):
    // 1. 空表：任何位序都越界，必须失败
    L = [];           断言 remove(L, 0) 失败
    // 2. 表头：删首元素，后继前移
    L = [a, b, c];    断言 remove(L, 0) == a 且 L == [b, c]
    // 3. 表中：删中间元素
    L = [a, b, c];    断言 remove(L, 1) == b 且 L == [a, c]
    // 4. 表尾：删末元素，其余不动
    L = [a, b, c];    断言 remove(L, 2) == c 且 L == [a, b]
    // 5. 越界：i == n 与 i == -1 都必须失败，且表内容不变
    L = [a, b, c];    断言 remove(L, 3) 失败 且 L == [a, b, c]
    L = [a, b, c];    断言 remove(L, -1) 失败 且 L == [a, b, c]
    // 6. 重复元素：删除按位序进行，不受重复值影响
    L = [a, b, a];    断言 remove(L, 2) == a 且 L == [a, b]
    L = [a, b, a];    断言 remove(L, 0) == a 且 L == [b, a]
```

**C 实现。**

```c
#include <stdbool.h>

#define MAX_SIZE 100

typedef int ElemType;  /* 元素类型；可用 typedef 泛化为其他类型 */

typedef struct {
    ElemType data[MAX_SIZE];
    int size;          /* 当前元素个数 */
} SeqList;

/* remove：删除并返回位序 i 的元素；前置条件 0 <= i < size，违反时失败 */
bool seqlist_remove(SeqList *L, int i, ElemType *out) {
    if (i < 0 || i >= L->size) {   /* 空表时 size == 0，任何 i 都越界 */
        return false;
    }
    *out = L->data[i];
    for (int j = i; j < L->size - 1; j++) {
        L->data[j] = L->data[j + 1];   /* 从被删位置起依次前移 */
    }
    L->size--;
    return true;
}
```

**复杂度分析。** 删除位序 $i$ 需移动 $n-1-i$ 个元素：最坏（$i=0$，删表头）$O(n)$；若 $i$ 在 $[0,n-1]$ 上均匀分布，平均移动 $\frac{(n-1)+0}{2}\approx n/2$ 个，$O(n)$；删表尾 $O(1)$。空间上原地操作，附加空间 $O(1)$。

**常见错误与变式。** 常见错误：删除后未前移元素或未减小 size，使表尾残留旧值，`size()` 与内容不一致；混淆「按值删除」与「按位序删除」两个接口。变式与迁移：把上面测试序列中的 $L$ 换成任意实现——顺序表、单链表、双链表——只要它们实现同一组签名与语义，**同一份测试原样运行，无需修改**。这正是契约测试（黑盒测试）的价值：测试锚定的是 ADT 契约而非存储细节；若某个实现让任一断言失败，说明它违反契约，而不是测试写错。若实现额外支持按值删除 `remove_value(v)`，则应补充「删除第一个匹配项」「值不存在时失败」两组用例。

## 易错点

- **把 ADT 绑定具体实现。** 认为「线性表就是数组」或「插入必须移动元素」。线性表是逻辑结构，顺序表与链表是存储结构；前者回答「是什么关系」，后者回答「怎么存」。判断一个说法属于哪一层，是本章最基本的练习。
- **下标域写错。** get/set/remove 的合法域是 $[0,n)$，insert 是 $[0,n]$。多写一个或少写一个位置，都会在表尾与空表两个边界上出错；与 1 起始教材对照时忘记位序差 1。
- **失败方式不统一。** 同一 ADT 内，get 越界返回特殊值、remove 越界抛异常、find 未找到返回 0——三种策略混用会让调用方无法建立统一的错误处理路径。契约表必须逐行写死。
- **忽视空表边界。** 空表上 get、set、remove 的任何位序都越界，insert 只有 $i=0$ 合法。「先查 size 再访问」的调用习惯能规避大多数空表错误，但契约测试仍必须显式覆盖空表。

## 小结

本节完成线性表的两步抽象。第一步是定义逻辑结构：$n\ge 0$ 个同类型元素组成的有序序列，表头无前驱、表尾无后继，其余元素有唯一的直接前驱与直接后继。第二步是用 (D, R, P) 三元组与操作契约表把行为固化为 ADT：逐操作写清前置条件、后置条件与失败方式，并用复杂度预算约束实现的质量下限。贯穿全节的结论是：线性表「能做什么」与「怎么存」是两层问题，接口冻结在先，存储选择在后。下一节起进入存储结构：[顺序表](./02-sequential-list.md) 用连续空间实现这些契约，[单链表](./03-singly-linked-list.md) 用指针链实现，两者共享本节定义的全部语义——这正是 ADT 的复用价值。配套实验见[顺序表实验](../../labs/chapter-01/lab-01-01-sequence-list/README.md)与[链表实验](../../labs/chapter-01/lab-01-02-linked-list/README.md)。
