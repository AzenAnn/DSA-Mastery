# 1.1 线性表的抽象数据类型

## 学习目标

- 能把线性表描述为一组数据与操作的契约；
- 能为操作写清前置条件、结果和失败方式；
- 能使用同一组测试比较不同实现。

## 数据对象

设线性表为 $L = (a_0, a_1, \ldots, a_{n-1})$，其中元素类型相同，`n` 为当前长度。这里采用从 `0` 开始的下标，并规定合法访问位置满足 $0 \le i < n$。

## 最小操作集合

| 操作 | 行为约定 |
| --- | --- |
| `size()` | 返回当前元素个数 |
| `is_empty()` | 判断线性表是否为空 |
| `get(i)` | 返回位置 `i` 的元素；越界时失败 |
| `set(i, value)` | 修改位置 `i` 的元素；越界时失败 |
| `insert(i, value)` | 在位置 `i` 前插入；允许 `i = n` |
| `remove(i)` | 删除并返回位置 `i` 的元素 |
| `find(value)` | 返回首次出现的位置，未找到时返回约定结果 |
| `clear()` | 删除全部元素并回到空表状态 |

## 边界约定

接口设计需要统一回答：空表删除如何处理？越界是返回特殊值、抛出异常，还是返回结果对象？元素能否为空值？这些都不应由实现临时决定。

本项目的示范实现可以选择一种语言惯用方式，但测试必须覆盖：

- 空表访问与删除；
- 在表头、表中和表尾插入；
- 删除后长度变化；
- 重复元素的查找；
- 非法下标。

## 复杂度预算

ADT 不要求固定复杂度，但可以为实现设定期望。例如 `get(i)` 在顺序表中期望为 `O(1)`，在单链表中允许为 `O(n)`。把复杂度写进文档可以防止“结果正确但实现退化”。

## 小结

ADT 把使用者关心的行为与内部存储分离。先冻结操作契约，才能公平地实现、测试和比较顺序表与链表。

## 练习

1. `insert(i, value)` 的合法下标范围为什么与 `get(i)` 不同？
2. 为 `remove(i)` 写出前置条件与后置条件。
3. 设计一段不依赖内部存储方式的线性表测试流程。
