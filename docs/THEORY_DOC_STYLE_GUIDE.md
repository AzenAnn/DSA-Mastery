# DSA Mastery 理论文档样式指南

本指南定义 DSA Mastery 教材中的理论语义、行内强调和代码标注写法。目标是让作者先选择内容的语义，再由站点统一决定浅色、深色和移动端的表现。不要用容器颜色代替正文中的明确判断，也不要在 Markdown 中写任意颜色值。

## 设计原则

1. **语义先于装饰**：定义、定理、证明、复杂度等类型必须与内容含义一致。
2. **标题直接可读**：颜色之外始终保留中文标题、短代码和边框形态，确保色觉差异或打印场景仍可辨认。
3. **一个块只承担一个角色**：不要为了“更醒目”把普通段落连续包进多个理论块。
4. **正文保持完整**：容器支持列表、表格、链接、公式、行内代码和 fenced code；不要把核心解释压缩成只有标签的卡片墙。
5. **作者不指定主题颜色**：只使用本文列出的容器和有限语义类，浅色/深色由主题令牌自动适配。

## 容器选择表

| 语法 | 默认标题 | 适用内容 | 不应使用的场景 |
| --- | --- | --- | --- |
| `definition` | 定义 | 术语、对象、关系的严格约定 | 一般背景介绍 |
| `theorem` | 定理 | 需要论证的重要结论 | 未经论证的经验建议 |
| `lemma` | 引理 | 为后续定理服务的中间结论 | 独立的主要结论 |
| `corollary` | 推论 | 从既有结论直接导出的结果 | 需要独立长证明的结论 |
| `property` | 性质 | 对象稳定具有的特征 | 操作步骤 |
| `proof` | 证明 | 定理、性质或复杂度结论的证明 | 只有最终答案的段落 |
| `intuition` | 直觉 | 帮助形成心智模型的非严格解释 | 替代正式定义 |
| `example` | 示例 | 正向实例和完整演算 | 反面情形 |
| `counterexample` | 反例 | 否定错误猜想的实例 | 一般警告 |
| `complexity` | 复杂度 | 时间/空间复杂度结论与前提 | 只出现一个 `O(...)` 的普通句子 |
| `pitfall` | 易错点 | 常见误解、边界和危险假设 | 可忽略的小提示 |

原生 `info`、`note`、`tip`、`important`、`warning`、`danger`、`caution` 和 `details` 仍然可用。它们适合通用提示、操作提醒和可折叠补充，不替代理论语义。

## 理论容器语法

标题写在容器类型之后；省略标题时使用上表中的中文默认标题。编号不自动生成，如需编号应由作者显式写入标题。

```md
::: definition 定义 1 · 线性表
线性表是由有限个数据元素组成的序列。
:::

::: theorem 定理 1 · 顺序表访问
顺序表按下标访问元素的时间复杂度为 $\Theta(1)$。
:::

::: proof
元素地址可由首地址和下标通过常数次算术运算得到。
:::
```

全部类型的最小写法：

```md
::: definition
定义正文。
:::

::: theorem
定理正文。
:::

::: lemma
引理正文。
:::

::: corollary
推论正文。
:::

::: property
性质正文。
:::

::: proof
证明正文。
:::

::: intuition
直觉解释。
:::

::: example
正向示例。
:::

::: counterexample
反例正文。
:::

::: complexity
令 `n` 为元素数，时间复杂度为 $\Theta(n)$。
:::

::: pitfall
明确说明容易混淆的概念。
:::
```

容器正文可以包含完整 Markdown：

```md
::: property 性质 · 栈的后进先出
- 后插入的元素先删除；
- `push` 和 `pop` 只作用于栈顶；
- 对数组栈而言，常见实现中的单次操作为 $\Theta(1)$。

| 操作 | 位置 |
| --- | --- |
| `push` | 栈顶 |
| `pop` | 栈顶 |

参见[线性表章节](/content/chapter-01-linear-list/00-overview)。
:::
```

## 原生 callout

通用提示继续使用 VitePress 原生语法：

```md
::: tip 学习建议
先手算一个小规模样例，再阅读实现。
:::

::: warning 前置条件
调用前必须保证下标合法。
:::

::: details 查看推导过程
这里放置可选的补充推导。
:::
```

不要把“定义”写成 `tip`，也不要为了获得警示色把反例写成 `danger`；应分别使用 `definition` 和 `counterexample`。

## 行内语义

使用 `==关键结论==` 生成语义高亮。高亮适合一行中的少量关键结论，不适合整段、标题或连续多项列表。

```md
==逻辑结构不等于存储结构==。

`a == b` 是行内代码，不会被高亮。

数学公式 $a == b$ 仍由 MathJax 处理。
```

术语首次正式定义可使用 `<dfn>`，键盘操作可使用 `<kbd>`：

```md
<dfn>抽象数据类型</dfn>只约定行为，不限定实现。

按 <kbd>Ctrl</kbd> + <kbd>K</kbd> 打开搜索。
```

确需对短文本表达语义时，只能使用以下有限类：

```html
<span class="dsa-text-accent">概念关联</span>
<span class="dsa-text-success">成立或完成</span>
<span class="dsa-text-signal">风险或反例</span>
<span class="dsa-text-muted">辅助信息</span>
```

禁止 `style="color: ..."`、自定义十六进制颜色或用颜色作为唯一信息载体。

## 代码框与文件名

普通 fenced code 可在 info string 末尾写 `[文件名]`，文件名会显示在代码工具栏中：

````md
```cpp:line-numbers {3} [binary-search.cpp]
int middle(int left, int right) {
    return left + (right - left) / 2;
}
```
````

代码组继续使用 VitePress 原生 tabs；组内 `[文件名]` 只作为 tab 名，不会重复出现在代码工具栏：

````md
::: code-group

```cpp [array.cpp]
int values[8]{};
```

```cpp [vector.cpp]
std::vector<int> values(8);
```

:::
````

长文件名和长代码只应在代码表面内部滚动，不应使整个页面横向滚动。

## Shiki 行标注

沿用 VitePress/Shiki 原生注释标记，标记注释不会显示在最终代码中：

````md
```cpp:line-numbers [annotations.cpp]
int kept = 1;       // [!code highlight]
int focus = kept;   // [!code focus]
int added = 2;      // [!code ++]
int removed = 3;    // [!code --]
int risky = 4;      // [!code warning]
int invalid = 5;    // [!code error]
```
````

- `highlight`：普通重点行；
- `focus`：聚焦该行并弱化其他行；
- `++` / `--`：差异新增/删除，带符号与颜色；
- `warning` / `error`：风险/错误行，带背景和边缘标记；
- `{3-5}`：也可在 fence info 中按行号高亮；
- `:line-numbers`：显示行号，`:no-line-numbers`：显式关闭。

不要手写 Shiki 生成的 HTML 类，也不要通过 HTML 复制按钮或代码组运行时。

## 正确与错误示例

正确：内容类型明确，标题说明对象，正文给出前提。

```md
::: complexity 二分查找 · 最坏情况
在输入有序且使用随机访问序列时，最坏时间复杂度为 $\Theta(\log n)$。
:::
```

错误：只为强调外观选择定理，且缺少前提。

```md
::: theorem 红色重点
二分查找很快。
:::
```

正确：一段只高亮真正需要记住的判断。

```md
大 O 描述渐近上界，==不天然等于最坏情况==。
```

错误：整段高亮或用任意颜色参数。

```md
==整段内容全部高亮会削弱层级。==

<span style="color: red">不要这样写。</span>
```

## 浅色、深色与移动端注意事项

- 不在正文中假设背景一定为白色或黑色；所有语义色由主题切换。
- 图片、图表和内嵌 SVG 仍需单独检查浅色与深色对比度。
- 不用“绿色那一行”“看红色框”等只依赖颜色的指代；写出类型或结论名称。
- 文件名宜简短且可识别。代码可以横向滚动，但段落、标题和表格外的页面根节点不能溢出。
- 不用连续空格模拟对齐；代码放 fenced code，键位放 `<kbd>`。
- 动效不是理论语义的一部分；系统会遵守 `prefers-reduced-motion`。

## 从旧定义语法迁移

只迁移确实是正式定义的块，不做全仓机械替换。

旧写法：

```md
::: info 定义：数据结构
数据结构是……
:::
```

新写法：

```md
::: definition 定义 · 数据结构
数据结构是……
:::
```

迁移时保持知识正文和结论不变，仅调整容器类型与标题格式。普通背景说明仍保留 `info`；经验建议使用 `tip`；严格结论再根据语义选择 `theorem`、`property` 或 `complexity`。完成后至少运行内容校验、构建和 Pages 浏览器测试，并在浅色/深色、390px/1440px 下检查实际页面。
