# Lab 00-02：用操作计数观察增长趋势

## 目标

大 O 记的从来不是「秒数」，而是「基本操作执行了多少次」。这个 Lab 让你亲手把这句话跑出来：写三个函数，让它们的基本操作次数分别近似 `1`、`n` 和 `n²`，再把结果填成一张表，亲眼看到增长趋势的差距，而不是记住一句「平方比线性快」。

做完之后，你应该能：

- 说清「时间复杂度」数的是**基本操作的次数**，不是运行时间；
- 用自己的实验数据验证 `O(1)`、`O(n)`、`O(n²)` 的增长趋势；
- 说明为什么同一段代码的计时会波动，以及该怎样测才更稳。

## 建议用时

45～60 分钟。跑代码本身只要几分钟，大部分时间应花在「预测 → 验证 → 解释偏差」上。

## 前置知识

- 会写最基础的循环（`for`）即可；
- 读过 0.3 节，知道「基本操作」「输入规模」「增长阶」这三个词各指什么；
- 参考代码用 C++，你也可以用 Python / Java，但**计数器必须是自己显式写的**，不能靠语言或工具替你数。

## 先预测，再验证

跑代码之前，先在纸上填出你对 `n = 1000` 的预测：

| 函数 | 你预测它执行多少次基本操作 |
| --- | --- |
| 常数（O(1)） | ______ |
| 线性（O(n)） | ______ |
| 平方（O(n²)） | ______ |

填完再跑代码，看差在哪。如果预测错了，错的那一步，就是你对「循环次数」理解里真实的漏洞——这正是这个 Lab 要抓出来的东西。

## 任务

### 1. 编写三个函数，使基本操作次数分别近似 1、n、n²

定义清楚你的「基本操作」是什么（一次加法、一次比较、一次访问，选一个并写下来），然后写三个函数：

- 一个与 `n` 无关，基本操作恒为常数；
- 一个单层循环，基本操作约执行 `n` 次；
- 一个双层循环，基本操作约执行 `n²` 次。

### 2. 对 n = 10、100、1000 记录操作次数

用计数器把三个函数在各规模下的操作次数记录下来；如果平方函数在 `n = 1000` 时已经慢到不想等，可以减小最大输入，但要说明你减到了多少、为什么。

### 3. 整理成表格，写出每个函数的时间复杂度判断

把三组规模 × 三个函数的操作次数填进一张表，并为每个函数写下它的时间复杂度（用 Θ 或 O 均可，但要写全「以什么为基本操作、以什么为输入规模」）。

### 4. 任选一个函数测量运行时间，说明计时为何可能波动

选一个函数，用墙钟时间测它跑一次要多久。至少跑 2～3 次，观察结果是否每次一样；如果不一样，说明波动可能来自哪里。

## 代码脚手架

下面是可以直接复制编译的参考代码。你也可以先自己写，遇到「计数对不上」再回头对照。

### 计数器模板（三个函数 + 一张表）

```cpp
#include <cstdio>

// 全局计数器：记录「基本操作」执行了多少次
long long ops = 0;

// O(1)：与 n 无关，只做固定次数的工作
long long constant_ops(int n) {
    ops = 0;
    int first = n;   // 基本操作：一次访问
    ops++;
    return first;
}

// O(n)：循环 n 次，每轮做一次基本操作
long long linear_ops(int n) {
    ops = 0;
    long long total = 0;
    for (int i = 0; i < n; i++) {
        total += i;  // 基本操作：一次加法
        ops++;
    }
    return total;
}

// O(n²)：两层循环，共 n*n 次基本操作
long long quadratic_ops(int n) {
    ops = 0;
    long long pairs = 0;
    for (int i = 0; i < n; i++) {
        for (int j = 0; j < n; j++) {
            pairs += (i == j);  // 基本操作：一次比较
            ops++;
        }
    }
    return pairs;
}

int main() {
    for (int n = 10; n <= 1000; n *= 10) {
        constant_ops(n);
        printf("n=%4d  O(1):   %5lld 次\n", n, ops);
        linear_ops(n);
        printf("         O(n):   %5lld 次\n", ops);
        quadratic_ops(n);
        printf("         O(n^2): %5lld 次\n", ops);
    }
    return 0;
}
```

编译运行：

```bash
g++ -O2 -o counter counter.cpp
./counter
```

::: tip 看清楚「计数」和「被计数的操作」是两回事
上面每个函数里，`total += i` 这类才是「基本操作」，紧跟着的 `ops++` 只是计数器在同步加一。别把 `ops++` 当成基本操作本身——那样数出来的永远是「计数器的自增次数」，不是算法真正做的工作。
:::

### 计时模板（任选一个函数测运行时间）

```cpp
#include <cstdio>
#include <chrono>

using namespace std::chrono;

long long linear_ops(int n) {
    long long total = 0;
    for (int i = 0; i < n; i++) total += i;
    return total;
}

int main() {
    const int n = 10000000;
    long long result = 0;

    // 跑 3 次取最小，避免某次被系统负载拖慢
    double best = 1e18;
    for (int r = 0; r < 3; r++) {
        auto t0 = steady_clock::now();
        result = linear_ops(n);
        auto t1 = steady_clock::now();
        double ms = duration<double, milli>(t1 - t0).count();
        if (ms < best) best = ms;
    }

    // 结果必须输出，否则编译器可能把整段循环当成无用代码删掉
    printf("linear_ops(%d) = %lld，最短耗时 %.3f ms\n", n, result, best);
    return 0;
}
```

编译运行：

```bash
g++ -O2 -o bench bench.cpp
./bench
```

多跑几次 `./bench`，观察每次打印的「最短耗时」是否稳定。

## 提交物

- 可运行代码（计数器 + 计时）；
- 一张操作次数表（3 组规模 × 3 个函数）；
- 100～200 字结论，说明你观察到的增长趋势和计时波动来源。

## 约束

- 基本操作必须是你**自己定义并显式计数**的，不能直接 `printf` 一个数糊弄；
- 计数器统计的必须是明确写出的基本操作，而不是「循环变量的自增」；
- 计时必须用墙钟时间（`chrono` 或 `clock_gettime`），不能用操作次数反推「耗时」；
- 计时的结果必须输出到屏幕上，否则编译器会优化掉整个循环。

## 验收标准

- [ ] 三个函数的计数器统计的是明确写出的基本操作（代码里能看到「基本操作 + 紧邻的 `ops++`」）；
- [ ] 实验至少包含 `n = 10、100、1000` 三组（若减小最大输入，已写明减到多少、为什么）；
- [ ] 表格里 O(1) 一列恒为常数、O(n) 一列约等于 `n`、O(n²) 一列约等于 `n²`（允许因定义不同差常数倍，但趋势必须一致）；
- [ ] 每个函数都写明了时间复杂度，且写清了「以什么为基本操作、以什么为输入规模」；
- [ ] 计时至少跑了 2 次，并说明为何取最小/平均，而不是只跑一次就下结论；
- [ ] 结论里没有把 `O(n)` 说成「固定秒数」；
- [ ] 至少指出一个计时误差来源（如 CPU 负载、编译器优化、计时精度、缓存）。

## 加分项

增加一个每次把问题规模减半的函数，观察 `O(log n)` 的增长趋势。参考骨架：

```cpp
// O(log n)：每轮把 n 减半
long long log_ops(int n) {
    ops = 0;
    while (n > 1) {
        n /= 2;  // 基本操作：一次除法
        ops++;
    }
    return n;
}
```

把它的数据加进同一张表，观察：当 `n` 从 10 涨到 1000，`O(log n)` 的操作次数才从 3 涨到 9 左右——这是「每步排除一半」和「每个都数一遍」的本质区别。

## Review 提示

审阅者可把 `n` 加到 `10000` 看平方函数是否明显变慢、把计时函数连续多跑几遍看波动；或检查被计数的「基本操作」是否真的和算法工作相关（而不是在数一个与规模无关的空循环）。
